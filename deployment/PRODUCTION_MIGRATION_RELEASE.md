# Production migration releases

Status: implementation prepared locally; not activated or production-verified. No historical migration is asserted to be applied by adding the manifest. Read this before merging database-dependent code into main.

## Architecture and current findings

| Environment | Application | Database | History |
| --- | --- | --- | --- |
| Local testing | npm run dev | Separate local-testing Supabase project | centerpro_setup.applied_migrations; unchanged development runner |
| Staging | development / Vercel Preview | centerpro_staging | 065 reportedly recorded in Supabase CLI history; older history unresolved |
| Production | main / Vercel Production | centerpro-erp | Existing legacy schema; manual SQL possible; history unresolved |

The original package build was `next build`, with no production SQL hook. No repository Vercel configuration or CI migration deployment existed. Legacy deployment guides use SQL Editor followed by application release. `supabase/config.toml` is configuration, not proof of migration completion. No hosted Vercel settings were accessible through available tools during implementation; no settings or database were accessed or changed. An operator must inspect Git production branch, build overrides, automatic domain assignment, system environment-variable exposure, environment scoping, existing integrations, deployment checks, deploy hooks, and permissions before activation. Do not print secret values during inspection.

The new build command runs a read-only release-ledger check before Next.js **only for Vercel Production**. Preview and local development do not use production credentials. Production with missing configuration, absent baseline or any pending manifest file fails before compilation. Unknown Vercel environments fail closed. Neither build nor start executes migrations. Keep VERCEL_ENV/system variables enabled; an override to `next build`, an older deployment, CLI deployment, or a promotion can bypass the repository build gate. The build gate alone is not a hosted publication policy.

## Activation prerequisites: mandatory before a main merge

1. Establish controlled production publication outside this repository: disable automatic production domain assignment and use staged **Production-environment** builds with manual promotion, or configure a verified required Vercel Deployment Check. If the account cannot enforce a check, use a controlled manual release and disable the competing automatic publication path. Preserve development Preview automation. These are future approved operator actions; this implementation changes no hosted settings.
2. Test the publication gate with a failing candidate and confirm the old production deployment remains live. Record the setting, project/team, approver, tested commit, result, and timestamp. Restrict bypass/promotion permissions. Do not merge dependent application code until this is proven. The initial adoption commit also needs controlled publication because no production ledger exists yet.
3. Protect main and require `Migration release validation / validate`. Protect workflow, runner, manifest and SQL changes with review. GitHub environment `production-migrations` must have required reviewers, prevent self-review where available, and allow only main. Verify your GitHub plan/repository supports these controls; otherwise use the documented manual operator procedure instead of enabling an unprotected workflow.
4. Set a verified production project reference as an environment variable and a separate write connection secret in that protected environment. Do not put database write credentials in Vercel. Provision a separate read-only verifier login with CONNECT, USAGE on centerpro_release and SELECT on its ledger only, and a read-only default transaction setting. Grant these explicitly after baseline creation; no grants are automatically widened by this tool. Keep this private schema outside Supabase Data API exposure. Confirm anon, authenticated and service_role cannot read or write it. Use the verifier's connection in Vercel Production only, under CENTERPRO_RELEASE_DATABASE_URL, and in CI as CENTERPRO_RELEASE_READONLY_DATABASE_URL. Both tools also require CENTERPRO_RELEASE_PROJECT_REF. No public/client prefix and no service-role API key is used.
5. Use a verified TLS direct connection on 5432 or session pooler on 5432. Transaction poolers, URL parameters and disabled certificate validation are rejected. Supply trusted CA configuration through your runtime trust store if necessary, never disable TLS verification. Direct connections may require IPv6. The target reference is a trusted operator allowlist, not an autodetected project name.
6. Reconcile production history and rehearse recovery before enabling writes. This requires new authorization to inspect production and later to record a baseline. A workflow dispatch alone must not substitute for review.

The read-only verification URL must authenticate as the dedicated `centerpro_release_verifier` Postgres role, never `postgres`. Use `centerpro_release_verifier.<project-ref>` as the username with the Supavisor **session pooler on port 5432**, or `centerpro_release_verifier` with the direct host if IPv6 is available. Give the role `CONNECT`, private-schema `USAGE`, ledger `SELECT`, and an explicit RLS `SELECT` policy for that role only. The application build gate rejects privileged logins. The write runner separately requires the `postgres` role and explicit authorization.

## Commands and guarantees

Run `npm run db:plan:release` without credentials. This validates local filenames, ordering, classifications and SHA-256 checksums and prints the manifest digest and identities. It does not parse/execute SQL or report remote pending status. Plan output is safe to retain; it contains no database state or secrets.

`npm run db:verify:release` is a future explicitly invoked connection. It uses a repeatable-read READ ONLY transaction, never initializes history, and prints pending identities. It returns nonzero if anything is pending or inconsistent, making it suitable for a publication gate. Do not run it against production without authorization. It verifies recorded history, not live schema equivalence: manual schema drift requires separate catalog review.

`npm run db:baseline:release -- <approval-path>` writes reviewed baseline records without running historical SQL. `npm run db:apply:release -- <approval-path>` applies the explicitly approved pending prefix. Both require a clean checkout, exact HEAD commit, expected target, and CENTERPRO_RELEASE_WRITE=approved-production-release. No dotenv file is loaded. Keep approval files outside the checkout; never pass credentials as arguments. Approval artifacts are non-secret audit records, not digital signatures; trust comes from protected CI review and operator access control.

The controlled ledger is `centerpro_release.applied_migrations`, deliberately separate from both other histories. It stores ordinal, complete filename, SHA-256, kind, origin (baseline/executed/verified), commit, evidence and timestamp. The private schema/table revoke access from application roles and enable RLS without application policies. Only the release owner writes. A distinct advisory lock serializes baseline/apply, including independent operators; CI also serializes dispatches and does not cancel a running operation for a newer one. Lock contention fails immediately.

All existing ledger rows must match an exact manifest prefix. All checksums are checked before applying any SQL. Missing/deleted/renamed/inserted/reordered files fail. Each new migration and ledger insert share one transaction, with 12-second lock and 240-second statement timeouts. Failure stops later migrations. Prior commits remain committed; rerun an unexpired unchanged approval after investigation to resume. A connection lost after commit is resolved by reading the ledger; a committed file is not run twice. These guarantees cover transactional database effects, not external side effects initiated by arbitrary SQL. Prohibit such side effects in review.

The runner removes only recognized outer BEGIN/COMMIT wrappers and rejects top-level transaction/session control and nontransactional operations. This is a conservative lexical guard, not a PostgreSQL validator or sandbox; SQL remains reviewed trusted code. Nontransactional migrations require a separately reviewed resumable procedure. No destructive reset, seed, automatic grants repair, down migration, CLI history repair or production bootstrap user is included.

## Immutable migration manifest

`deployment/migrations/manifest.json` includes every current SQL filename, including 008a/008b and both 043 files. `043_verify_bank_management.sql` is classified as verification, not DDL. Its queries are not automatically run against customer data. Baseline review records that its verification was reviewed; a future verification-only entry requires `verification_evidence[filename]` before the apply command records origin verified without executing it.

Checksums use UTF-8 with CRLF converted to LF, then SHA-256. This avoids Windows checkout-only checksum drift and **differs from the development runner's raw-text hashing**. Do not copy checksums between ledgers. Do not modify existing SQL or normalize it on disk. Append new files and manifest entries with reviewed checksums and a new later identifier; do not sort an inserted historical file into an already-established prefix. The PR check compares the complete old manifest prefix (or base-commit SQL at initial adoption) and rejects history changes even if a new manifest checksum was supplied. Protect that check through branch rules; a manifest by itself is editable.

## Historical baseline procedure (one-time, per database)

1. Obtain separate authorization for read-only production inspection. Confirm actual target using the project dashboard and deployment environment, not display name alone. Gather both existing ledgers if present, SQL Editor/deployment records, schema/catalog exports and function definitions. Keep customer data and credentials outside Git and CI artifacts.
2. Reconstruct the expected effective schema through ordered replay in an isolated scratch environment. Compare effective functions, overloads, columns/types, constraints, indexes, RLS policies, grants and triggers. Later migrations replace earlier definitions; the mere existence of a table does not prove all prior files ran. Document reviewed equivalents or divergence and their rationale per file. Use current schema evidence plus deployment records rather than claiming an original historical execution from a current schema alone.
3. Classify each file as verified historically satisfied, pending, or unknown. A baseline must be a contiguous verified prefix. Do not infer 001-064 from a recorded 065, or infer production history from staging/local history. Unknowns block release. A hole beneath a later manually applied migration needs a specific reconciliation/forward-repair plan, not blind replay or fictitious ledger entries.
4. Preserve an encrypted backup, test restore and verify reconciliation evidence. Copy `approval.example.json` outside the checkout. Fill all common evidence fields, exact clean release commit, manifest digest, explicit baseline_count, and verified_files containing precisely that prefix's identities. No automatic baseline generator asserts that history is valid. Remove/ignore pending/through for this baseline operation.
5. Have another reviewer approve evidence and target. Dispatch the protected workflow with operation baseline, or use the operator command. It refuses any pre-existing release schema and creates all baseline rows atomically. It never modifies the CLI or development ledger. If an interrupted attempt left unexpected state, investigate; do not drop it to bypass the refusal.
6. Provision and test the read-only verifier. Verification may report genuine pending migrations: that is expected until approved apply completes. Do not deploy while verification fails.

Supabase CLI stores `supabase_migrations.schema_migrations`. The local-testing runner stores `centerpro_setup.applied_migrations`. Neither is automatically imported, trusted, repaired or updated by this workflow. Staging's CLI 065 row is evidence about that entry only; its older history still needs reconciliation. Do not use blind `supabase db push`, `migration repair`, or this local development setup against either legacy hosted database. Adopt one authoritative release ledger for production; a future CLI conversion needs its own reviewed mapping/baseline plan, especially for duplicate numeric prefixes.

## Approval artifact

Start with `deployment/migrations/approval.example.json`; its placeholders intentionally fail. Common fields bind version, project_ref, 40-character commit, manifest_sha256, approved_by, evidence_ref, backup_ref, backup_verified_at, restore_test_ref, recovery_plan_ref, deployment_gate_ref and expires_at. Backup verification must be within 24 hours, and expiry must be in the next 24 hours. These freshness checks validate attestations, not the existence/completeness of backup files or hosted settings; reviewers must verify those independently. Refresh evidence after a material change or expired approval.

For apply, set through to the last approved filename and pending to the exact contiguous identities approved for execution, including all missing predecessors. The runner cannot run unlisted files or skip a hole. A partially committed retry retains the original list; already recorded entries are skipped. New commits or changed manifests need new approval. Do not include passwords, connection strings, customer data, or backup contents in artifacts. References should be private record identifiers, not secret-bearing URLs.

## Production releases after baseline

1. Review new SQL and application compatibility in a PR to development. Run local release tests and ordered upgrade tests in an isolated environment representing production. Reconcile and update staging independently; merging into development does not itself apply SQL. Test Vercel Preview against centerpro_staging. Require UI/RPC/tenant/security and stock/financial checks for affected features.
2. Verify the external publication gate before merging the tested change into main. Record exact main commit. An automatic build may fail while migrations are pending; that is intentional and must leave current production live. Do not relax the gate to make the build green.
3. Perform backup and restore verification below. Confirm old code can operate with the new SQL. Prefer expand/deploy/contract across separate releases. For function/stock behavior changes or breaking operations, pause affected writes, background jobs and queued/offline clients through the cutover; a browser maintenance banner alone does not stop writers. Establish the reconciliation cutoff.
4. Generate the offline manifest plan; under separate authorization run read-only remote verification. Prepare the release approval list from known pending identities, including missing predecessors. Review prerequisites and current schema drift. Do not turn a missing ledger into an empty database assumption.
5. Dispatch `Approved production migration operation` on main, operation apply, with reviewed non-secret approval JSON. The protected environment reviewer checks backup/recovery and publication evidence before credentials become available. The workflow never triggers on a push/merge, never deploys and uses a clean checkout. If GitHub required-review environments are unavailable, a separately authorized operator uses the same command from a clean exact-commit checkout with secrets provisioned outside shell history.
6. Confirm read-only verification exits zero and run release-specific postconditions through an authorized operator. The workflow checks the ledger, not business semantics. If either fails, block publication and investigate. Keep the approved commit pinned; newer main commits must not slip into the release.
7. Rebuild the exact commit with Production environment configuration. Stage without domain assignment using the reviewed installed Vercel CLI (`vercel deploy --prod --skip-domain`), validate it, then explicitly promote that Production deployment after approval. Confirm installed CLI syntax with --help. Never promote a staging Preview that was compiled with staging credentials. Git automatic deployment must not race this operation. Record commit, deployment ID, manifest digest, ledger state and release evidence together.
8. Smoke-test login, permissions, critical RPCs and affected stock/cost/accounting flows. Resume writes only after checks pass, monitor, and sync development with main through the normal reviewed process. No production migration is added to npm dev, build or start hooks.

## Migration 065 specifically

Production 065 is unknown until verified. Staging's CLI record must not be copied into production. Inspect the current definitions of prepare_bom_completion(uuid) and complete_manufacturing_order(uuid), the legacy source-validation/order markers and all predecessors. The guarded string replacements are not a safe manual rerun mechanism: the first marker can still occur in modified text, while the second changes after application. Existing matching effects require reconciliation; missing/incompatible markers require investigation, not editing 065 or deleting checks.

If production is verified through 064, baseline that exact prefix and approve only 065. If already satisfied through 065, baseline it with evidence and do not replay. If earlier migrations are genuinely missing, approve them in dependency order only after upgrade rehearsal. Do not claim production is through 064 based on the filename alone.

Capture the two pre-release function definitions and grants securely. Rehearse 065 on an isolated predecessor schema, confirm automatic Milling FIFO and snapshot order, shortages/atomic rollback, duplicate and concurrent completion, Packing explicit selection, tenant isolation, historical completed records, and quantity/value reconciliation. There is no data backfill in 065, but the changed completion functions affect live writes before new UI goes live. Pause Milling completion if compatibility cannot be demonstrated. Recovery may restore reviewed function definitions via a NEW later migration; never edit 065 or undo already posted stock/cost entries by deleting them.

## Backup verification on Supabase Free

Do not assume Free provides downloadable daily backups or PITR. Supabase recommends off-site logical exports for Free; paid backup/PITR features require an eligible plan. Before every migration release, produce an encrypted off-site logical backup using reviewed, pinned Supabase CLI/pg_dump tooling and inspect its documented exclusions. Schema-only exports are insufficient. Capture required schema, data, sequences, grants/roles, extension inventory, Auth data/config needed for recovery, both migration ledgers and ownership dependencies. A default CLI dump may exclude managed schemas: explicitly verify coverage rather than claiming it is complete. Keep backup credentials in protected runtime configuration, not command arguments or logs.

Inventory Storage binaries separately: a database export contains metadata, not object contents. Separately inventory deployment/configuration, secret recovery ownership, Auth provider/redirect configuration and integrations. A database restore alone cannot recover these. Never attach dumps to public CI artifacts or commit them.

Verify backup completion, encrypted location, checksums, timestamp/cutoff, scope, retention and operator access. Restore to an isolated compatible PostgreSQL/Supabase environment and verify schema/functions/policies/grants, row counts, sequence state, tenant isolation, representative login and required balances/stock. Record actual restore duration (RTO), data cutoff/loss window (RPO), tooling versions and reconciliation results. Stop release if coverage or restore test is incomplete. If you need near-zero data loss or frequent recovery points, upgrade to appropriate backup/PITR capability or accept and document a write freeze around the logical snapshot. A timestamp field is not proof of recoverability.

## Failures and recovery

- SQL/ledger error before commit rolls back that file. Earlier files remain committed. Stop deployment, inspect restricted database logs without dumping secrets, correct the cause via reviewed new SQL where needed, and verify ledger before retry. CLI errors intentionally suppress raw database details to avoid leaking values.
- A process crash releases its session advisory lock when the connection closes. Check the actual ledger after a timeout/network failure; never assume failure means no commit. Do not delete successful history to force a rerun.
- A Vercel build/deploy failure after migration leaves the schema changed. Keep the old application only if compatibility was proved. Repair forward; do not automatically reverse migrations. A Vercel rollback restores code only and may be incompatible with new schema/data. Check old artifact and ledger compatibility before promoting it.
- After business transactions have posted, prefer compensating forward changes and reconciliation. Never delete stock, cost, cash or journal history to undo a release.
- Disaster restore needs explicit authorization: freeze all writers, preserve incident evidence and current data, establish the cutoff and lost-write reconciliation plan, restore into an isolated target first, verify all dependencies and Storage/config coverage, then perform a controlled cutover with application/environment changes. Free logical restore can lose writes after the snapshot. Revalidate release ledger against the restored database before publication; do not patch history to match the desired application.

## Local validation and limits

`npm run test:migration-release` uses a transaction-aware in-memory transport, temp files and child processes. It never connects to a database or executes migrations. It covers manifest drift/order, approvals, targets/TLS, baseline behavior, transaction failure/retry semantics, read-only verification and production/Preview gate behavior. `npm run db:plan:dev` retains its existing offline behavior. No full production build is needed to validate these scripts, and builds loading local credentials must not be used as a substitute for isolated validation.

These tests do not establish real PostgreSQL transaction/DDL behavior, TLS connectivity, lock concurrency, backup restorability, Vercel hosting enforcement, or production schema equivalence. Before activation, separately authorize an isolated PostgreSQL integration rehearsal (including two-session lock contention, crash-after-commit retry and role-denial tests), staging upgrade/QA, actual backup restore drill and hosted gate test. No hosted dependency is claimed complete by this implementation.
